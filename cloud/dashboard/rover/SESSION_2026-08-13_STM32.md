# Session 2026-08-13 — Rover 2 on the STM32 board, M2 completed

Rover 2 drove mission M2 successfully at the end of this session. This records
what changed and, more importantly, *why*, so none of it gets undone.

## The headline: the controller board was swapped and nothing knew

At the **2026-08-07 17:28 reboot**, USB port 1.3 changed from CP2102
(`10c4:ea60`) to CH340 (`1a86:7523`). The Yahboom MicroROS ESP32-S3 board was
replaced by a **Yahboom STM32 Rosmaster board, firmware 3.6**. Every service was
still written for the old one: `micro-ros-agent` pinned `-b 230400` while the
board speaks **Rosmaster protocol at 115200**, and there is no `0x7E` XRCE
begin-flag anywhere in its stream — it is not a micro-ROS client at all, so no
baud change could ever have produced a session. `/odom_raw`, `/imu`,
`/wheel_ticks` and `/battery` all had **publisher count 0**.

**New: `fpms_stm32_bridge.py` + `fpms-stm32-bridge.service`** replaces
`micro_ros_agent`. It speaks Rosmaster and republishes the identical contract
the rest of the stack already consumed, so nothing downstream was rewritten:

    /odom_raw  20 Hz   /imu  25 Hz   /battery  2 Hz   /wheel_ticks  2 Hz
    subscribes /cmd_vel, /cmd_duty, /estop, /bridge_arm, /fpms/mission/armed

`micro-ros-agent` and `fpms-uros-supervisor` are stopped, disabled and removed —
the supervisor had been power-cycling the board and restarting the executor
every ~5 minutes, failing recovery #29 in a row.

## The fix that actually won the mission

    FPMS_MISSION_TURN_WIRE_SIGN = -1      (was +1)

The rover reached M2, then turned the wrong way and its own guard aborted:
`asked -12.6deg, the rover rotated +8.1deg — the OPPOSITE way`. An abort skips
the retrace, which is why it never came back. The golden program agrees:
`fpms_phase6_M1_M2_WORKING.py:156  TURN_SIGN = -1  # PHASE5: flipped`.

## Arena (operator-measured)

Rectangular **1500 × 1400 mm** — the code assumed square, so `in_arena` and the
zone rects now use separate `ARENA_W_MM` / `ARENA_H_MM`. Zones are 3x smaller
(`ZONE_FRAC 0.10`) and the start box is the rover's own footprint
(`ROVER_LEN_MM 235`, from the measured **170 mm wheelbase** plus one 65 mm wheel).

    start (1322, 178)   zone-b/m2 (1365, 1265)   zone-a/m1 (135, 1265)   water (135, 135)

Four places had to move together or they silently disagree about "home": the
executor geometry, `fpms-tf.service`'s `map->odom` anchor, the console's
`RESET POSE` target (`FPMS_RESET_X_MM/Y_MM`), and the saved origin file.
`console.html` and `frontend/src/lib/arena.ts` were rescaled to match — at
x=1322 on a 1200 mm map the dashboard suppressed the rover glyph entirely and
showed "POSE ESTIMATE BROKEN".

Fast DDS shared memory is dead on this box: discovery succeeds and **no data
flows**. Only the units carrying that profile could exchange topics — that is
why `/scan_lidar` reached zero ROS subscribers until drop-ins were added.

## The golden program is directly reusable again

`fpms_phase6_M1_M2_WORKING.py` drives the **same class of Rosmaster board**, so
unlike the ESP32-era firmware its constants still apply:

    _TKMM = pi*70/1320 = 0.16657 mm/tick  =  6.00 counts/mm
    _DRV 26 duty · _TRN 50 · _COAST 0.93 · _HZ 20 · _KPH 10 · _FSTOP 120
    wheel order [M1,M2 = left, M3,M4 = right]  (:2469)
    forward = POSITIVE duty  (B6_FORWARD_POWER = 26, "PHASE5: flipped")

6.00 counts/mm independently matches the **6.12** measured on this board today.
`/cmd_duty` (`Int32MultiArray`, 4 ints, ±40) now exists on the bridge for this
path — the velocity path has a dead zone and a PID ramp, which is why short
segments kept aborting; raw duty has neither.

## Known-open

- **No localisation.** `try_arena_fix()` needs a live `map->odom`. No SLAM/AMCL
  runs; `fpms-tf.service` occupies that edge with a STATIC transform, and static
  transforms carry `stamp = 0` so the executor rejects them as ~1.79e9 s stale.
  `slam_toolbox 2.6.10` is installed and was proven to publish `map->odom` on
  this hardware; it needs a driven room map.
- **`base_footprint -> laser_frame` is a placeholder** `[0,0,0.1]`, x/y/yaw all
  zero, still marked MEASURE ME. 1 deg of mount yaw is ~10.5 mm of error.
- **`telemetry/residual` is documented and subscribed but never published.** Read
  per-segment residuals from `events/mission_done` -> `measured[]`.
- **The board resets its own odometry** occasionally (`/odom_raw RESET to the
  origin`), seen twice today. Re-anchor before a run if pose looks wrong.
- Duty polarity conflicts with the August ESP32 measurement; settle it with
  wheels off the ground before trusting `/cmd_duty`.
