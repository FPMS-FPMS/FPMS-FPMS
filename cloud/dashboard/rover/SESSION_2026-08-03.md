## THE SPINNING PROBLEM — read before running anything

The rover ended the session having spun roughly 440 degrees in place across
several tests. The direct cause was using `crawl_test.py --mode turn` as a
**liveness check**. That test performs four bounded turns (+0.6, +0.9, +1.2,
-1.2 rad/s for 2 s each, ~330 deg of total rotation), and a -113.3 deg re-face
was then needed to square the rover back up, adding more.

**Rule for next session: never use a turning test to check whether the board is
alive.** It disturbs the one piece of state that has no absolute reference on
this rover — heading. Use instead:
- a passive check: is `/odom_raw` pose CHANGING (not just publishing)?
- or a short straight-line probe, which leaves heading untouched.

A passive liveness check is available and sufficient: when the board partially
hangs (below), its published pose becomes **bit-identical** between samples
while the topic still runs at 50 Hz. Comparing two pose samples a second apart
detects it with no motion at all.

**Do not assume this fully explains what the operator saw.** If the rover spins
continuously without being commanded to, that is a different and more serious
fault (runaway angular command, or a stale non-zero Twist being republished) —
check for a stuck publisher on `/cmd_vel` before anything else.

## MEASURED DRIVETRAIN TRUTH (2026-08-04) — use these, they are operator-verified

Established by OPEN-LOOP tests the operator watched, after every sensor-based
test had produced confident wrong answers.

**Motor polarity — the right side is wired opposite to the left.**
Driving all four on IN_A at equal duty: LEFT ran forward, RIGHT ran backward,
so the rover spun. Fix, now in `fpms_config.h`:

    MOTOR1_INV false   // front-left  (board M3)
    MOTOR2_INV true    // front-right (board M1)  <- wired opposite
    MOTOR3_INV false   // rear-left   (board M4)
    MOTOR4_INV true    // rear-right  (board M2)  <- wired opposite

**Encoder signs — only the LEFT pair is inverted.**
Slow forward crawl, all four driven forward:
`M1 +20288, M2 +19988, M3 -18730, M4 -17677` — right counts up, left counts down.

    MOTOR1_ENCODER_INV true    MOTOR2_ENCODER_INV false
    MOTOR3_ENCODER_INV true    MOTOR4_ENCODER_INV false

Inverting all four (an earlier wrong reading) made a commanded 564mm produce
-2080mm of phantom travel and drove the rover into a wall.

**COUNTS_PER_MM ~= 14.8.** Operator measured 800mm of real travel where the
encoders reported 11836 counts. An earlier value of 27.7 came from a rough
eyeball estimate and was 1.9x too high — do not reuse it. Re-measure against a
tape before trusting any distance.

**Open-loop crawl that works:** base duty 58 with per-wheel trim
`{0.820, 0.839, 0.914, 1.000}` (chasing the slowest wheel), plus a **kick-start**
of duty 140 for 220 ms. Without the kick the motors only buzz at crawl duty and
the rover does not move at all — the operator heard this as a beep.

**Mechanical:** the top-left wheel came off during a reverse leg. Wildly unequal
encoder counts across wheels (740mm vs 203mm on one leg) mean SLIP or a
mechanical failure, not travel. A slip detector — abort if the four wheels
disagree by more than ~15% — would catch it; the "no counts" failsafe does not,
because slipping wheels still produce counts.

## DANGER — THE BOARD IS LEFT RUNNING A SELF-REPEATING MOTOR TEST

**The drive board currently holds `enctest` firmware, NOT the mission firmware.**
Its `loop()` re-runs the eight-motor twitch sequence every 4 seconds **forever,
with no host involved**. Shutting down the Pi does NOT stop it — that was
discovered the hard way: the Pi was halted and the rover kept moving.

It was left halted in the ESP32 bootloader (`esptool --after no_reset`), which
stops it, but **any reset or power cycle restarts the test firmware.**

### FIRST ACTION NEXT SESSION, BEFORE ANYTHING ELSE

    cd ~/lino/firmware && ~/.platformio/penv/bin/pio run -e fpms -t upload

Never leave a test sketch with motor commands in `loop()` on this board. Put the
sequence in `setup()` and leave `loop()` empty, so it runs once and stops.

## THE ENCODER FIX — MEASURED, READY TO APPLY

Per-wheel test (`firmware_linorobot/tools/enc_main.cpp`), two clean passes:

| motor | own encoder on FWD | own encoder on REV |
|---|---|---|
| M1 | **-11802 / -12158** | +13015 / +11508 |
| M2 | **-16356 / -17199** | +13021 / +12808 |
| M3 | **-12835 / -11153** | +9419 / +8788 |
| M4 | **-10850** | +12824 |

**All four encoders count NEGATIVE when the motor is driven forward.** Pin
mapping is CORRECT — driving motor N moves encoder N; the small cross-counts are
chassis shake.

**Fix:** set all four `MOTORn_ENCODER_INV` to `true` in `fpms_config.h`, rebuild,
reflash. Then verify by asking the OPERATOR to watch a pure-forward command —
not with any odometry-based test, which is what got fooled.

## THE ODOMETRY LIES — TONIGHT'S "SUCCESSFUL" M2 RUNS WERE FALSE.

**Operator-verified 2026-08-03, late.** A command of `linear.x=+0.08, angular.z=0`
for 3 s made the rover **SPIN IN PLACE**. The sensors reported "moved 117 mm,
rotated -3.2 deg". Both numbers are lies.

Consequences — do not trust any of these:
- The two M2 runs reporting `drive asked 564mm measured 575mm` and
  `|err| 18.9mm` **did not happen**. The rover was spinning.
- `drivetrain_check.py` printing "DRIVETRAIN CORRECT" was fooled by the same
  lie. It used odometry for translation and the gyro for rotation.
- Any distance or heading figure in this file taken from odometry after the
  linorobot firmware was flashed is suspect.

**Mechanism: inverted ENCODER signs on some wheels.** The velocity PID reads a
negative RPM when it commanded positive, so error GROWS instead of shrinking and
that wheel saturates at full duty. Whichever wheel wins decides the direction,
which is why the operator reports the spin direction **varies between runs** — a
fixed wiring fault would spin the same way every time. The published odometry is
integrated from those same inverted encoders, so it reports clean forward travel
while the chassis rotates.

This only appeared with the new firmware because the vendor firmware was
effectively open-loop; a wrong encoder sign there could not run away.

### THE FIX — next session, before anything else

Identify which wheels are inverted. This fork has NO calibration source
(`firmware/src/` contains only `firmware.cpp`), so write a small standalone test
sketch that, for each motor in turn: drives it alone at a fixed low duty for ~1 s
and prints the encoder delta for ALL FOUR wheels. That gives, per wheel:
  - does its own encoder count UP when driven forward?  (sign)
  - does driving motor N move only encoder N?           (pin mapping)
Then set `MOTORn_ENCODER_INV` / `MOTORn_INV` in `fpms_config.h` from measurement
and reflash.

**Do not use any odometry-based test to verify the fix.** Ask the operator to
watch a pure-forward command. Their eyes are the only trustworthy instrument
until the encoders are proven.

## LIDAR RATE KILLS THE MICRO-ROS SESSION — real, but secondary to the above

**Measured 2026-08-03 evening.** With `FPMS_LIDAR_HZ=10` (~9.4 Hz `LaserScan`,
360 points, on the same Pi as the micro-ROS agent) the drive board went silent
within ~1-2 minutes of every reset, repeatedly, all evening.

Dropped to `FPMS_LIDAR_HZ=2` and the board ran **rock steady for 3 minutes**:

    t= 20s 1001 msgs/20s ALIVE      t=100s 1001 ALIVE
    t= 40s 1001 ALIVE               t=120s 1000 ALIVE
    t= 60s 1001 ALIVE               t=140s 1001 ALIVE
    t= 80s 1001 ALIVE               t=180s 1000 ALIVE

That is a flat 50 Hz with no drop-outs. The mechanism is almost certainly DDS/CPU
load starving the agent's serial reads at 921600, corrupting XRCE framing and
killing the session.

**This was self-inflicted**: the LiDAR was raised from 2.37 Hz to 9.4 Hz earlier
the same day by moving the MQTT broker onto the Pi. That change is good for Nav2
in isolation and bad for the micro-ROS link.

Next session, in order:
1. Keep `FPMS_LIDAR_HZ=2` until the link is proven stable for 10+ minutes.
2. Then try lowering the serial baud (921600 -> 460800) in BOTH `fpms_config.h`
   (`BAUDRATE`) and the `micro-ros-agent` unit (`-b`). 921600 on a CP2102 is
   marginal and is the other half of this suspicion.
3. Only then raise the LiDAR rate back, one step at a time, watching survival.

Do NOT treat the LiDAR rate and the board hang as separate problems again.

not power (measured at 13.18 V).

reset, motion and gyro both return immediately and correctly.

**This cost a mission run**: the first M2 attempt commanded 594 mm and travelled
0 mm over a 60 s timeout, which looked like a bug in the new mission code and
was not.

Next session: find the cause, and until then fold an automatic board reset +
pose-liveness verification into mission startup so a mission can never begin
against a hung board.

## OPERATIONAL NOTES EARNED THIS SESSION

- After a reflash the board can hold a **stale micro-ROS session**; one
  `micro-ros-agent` restart resyncs it.
- `fpms-odom-tf` must ALSO be restarted after the board's session is recreated,
  or it sits frozen on subscriptions to publishers that no longer exist (seen as
  `odom=16023` unchanged across three 30 s reports).
- The rover's DHCP address moves across reboots (`.110` -> `.141`). Helpers try
  a host list then mDNS.
- **In micro-ROS the CLIENT declares its DDS domain**, not the agent. Getting
  this wrong produces a flawless-looking agent session with `Publisher count: 0`
  on every topic.
- Any diagnostic added to this rover should carry **a control value whose
  correct answer is already known** (e.g. `WHO_AM_I`). Two gyro diagnostics
  returned all-zeros this session for reasons that were entirely artefacts of
  the instrument, and the control channel is what caught both.
